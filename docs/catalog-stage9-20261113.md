## Подготовленные исправления

1. Сравнение товара с API включает специальную цену, ожидаемое количество и дату поставки. Прежде изменение только этих полей могло не вызвать запись. Сравниваются исходные inventory-поля, чтобы постоянная корректировка витринного остатка не вызывала повторное вычитание. Ожидаемое количество сравнивается как число; дата API с временем приводится к DATE для сравнения.
2. Дата выполненного API-задания обновляется и при успешном получении данных без изменений цен/остатков, а также при обновлении только модификаций. Запуск без свежих ответов не выдаётся за успешное обновление.
3. Два CLI-входа API используют один путь блокировки на ID задания. Установка ждёт освобождения прежней и новой блокировки API и блокировки фида спецшин, не прерывая работающие процессы.
4. Приватные контрольные отметки фиксируют начало, завершение, длительность, счётчики, успех, неполные данные, ошибку или прерывание. Успешная сверка shadow не обновляет дату полного успешного live-запуска. Поздний завершитель старого run_id не перезаписывает более новый запуск.
5. Генерация спецшин читает согласованный снимок БД. Чужая транзакция не завершается; собственной транзакцией управляет генератор. Атомарная публикация XML сохранена. GIF исключён из допустимых форматов спецшин по требованиям Яндекс Товаров.
6. В YML подключено существующее описание товара: собственный текст либо однозначный действующий шаблон InSEO, по тому же обработчику, который использует проверка итоговых SEO-полей. Новые тексты не создаются. Пустое описание, неоднозначный шаблон или текст длиннее 3000 символов не заменяются выдуманным/обрезанным текстом; пропуск виден в диагностике. Нормальный собственный HTML переводится в текст без script/style. Исходные поля товара не переписываются.
7. Кабинет Яндекс Товаров показывает отдельные ошибки и предупреждения по файлам: ID, категории, цена, название, описание, URL, локальное фото и размеры. Ошибка чтения XML не сопровождается ложным сообщением об успешной проверке полей. Это выбранные проверки, а не полный валидатор площадки и не подтверждение модерации.
8. Новый экран `/admin/catalog-workflow/updates` объединяет состояние запусков, ограниченную контрольную сверку API и переход к диагностике файлов. Только GET и роль admin, без кнопок запуска или настройки расписания.

Отметки сохраняются в `storage/catalog-task-status`, вне публичного каталога: каталог 0700, файлы 0640, атомарная замена. Доступные через страницу счётчики ограничены белым списком; токены, ответы API целиком, XML и тексты исключений туда не попадают. Прочие старые генераторы пока представлены датами/диагностикой файлов; отсутствие новой отметки у них не считается ошибкой.

| ymlfid-kvadro.xml | 1 фото ниже внутреннего порога |
| export-yml-bb-spectyre.xml | 137 HTTP-ссылок; назначение B2B-выгрузки отличается от подключения к Яндексу |

Порог 450×450 — правило существующего генератора спецшин, а не универсальный минимум Яндекс Товаров. Актуальная справка требует JPEG/PNG/WebP, до 10 МБ и минимум 300×400. Новая диагностика различает эти два порога. Файл с изображением 300×400 не получает ошибку минимального размера из-за внутреннего порога 450×450.

Также установлено, что прежний генератор спецшин не выводил description вообще. Новый код подключает существующий текст; оставшиеся пропуски требуют работы с данными. Перенос всех описаний, переписывание текстов, массовая смена ID, устранение дублей старого кросс-фида, замена фото и настройка подключений фидов к площадке автоматически не выполнялись. Эти действия не следует смешивать с проверкой обновлений, особенно при отложенных правках товарных данных.

Правила сверены с [упрощённым типом предложения](https://yandex.ru/support/merchants/ru/offers) и [произвольным типом](https://yandex.ru/support/merchants/ru/export/vendor-model). При произвольном типе поддерживается сочетание vendor/model вместо обязательности отдельного name. Проверка всех элементов этого типа в текущую диагностику не входит.

## Публикация и контрольный запуск

Пакет: `outputs/stage9-release`, 13 файлов. Производственный runner: `outputs/stage9-runner.php`. Он не меняет расписание, проверяет исходные SHA256, защищается блокировками задач, делает резервные копии и выполняет проверки до/после установки. Приватная папка: `/home/s/shinaspec/catalog-stage9-20261113`.

`scripts/check_catalog_stage9.php` проверяет неизменность исходных таблиц и опубликованных XML во время установки, сравнивает ID/цены/фото/названия/характеристики генератора до/после, разрешая только подключение description, проверяет новую страницу и установленные SHA256. Наличие description и редакционных замечаний не выдаётся за изменение товарных данных или за успешную модерацию.

После подтверждённой публикации выполнить `scripts/check_catalog_stage9_manual.php` через SSH: ограниченный shadow-прогон для одного артикула, контрольная сверка двух товаров без записи в них, ручная генерация задания 32, проверка публичного HTTP 200 и совпадения файла. Предыдущий XML сохраняется в приватном пакете. Полный live-запуск задания 36 вручную этим сценарием не запускается. Никаких заданий планировщика не добавляется.

Локальные исходники до изменения сохранены в `outputs/stage9-local-baseline.json`. Локальный порядок журналирования интеграции Avito сохранён; производственные адаптеры собираются со свежего боевого baseline, а не полной копией локальных общих файлов. Не применять локальный адаптер повторно поверх уже изменённого файла. Не запускать производственный runner повторно при наличии receipt.
